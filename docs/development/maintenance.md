# 维护手册

面向单维护者的最低维护成本方案。目标是「一直能用、一直可信」，不追求活跃度。
所有命令在仓库根目录执行。

## 每次改动前

```bash
python scripts/check_all.py
```

不绿不提交。这是唯一的质量底线，没有例外。

## 每月（约 30 分钟）

1. 打开仓库的 Pull requests 页，处理 Dependabot 那个合并 PR。
2. 本地拉下来，跑 `python scripts/check_all.py`。
3. 绿了就合并；红了就看日志，通常是依赖的破坏性变更。
4. 打开 Security 页，确认没有未处理的告警。

Dependabot 已按月分组（见 `.github/dependabot.yml`），正常情况下每月只有一个 PR。

## 每季度（约 1 小时）

1. 决定是否发版。没有值得说的改动就不发 —— 空版本比不发更糟。
2. 发版按 [releasing.md](releasing.md) 执行。
3. 在 `CHANGELOG.md` 顶部加一节，写清这一季解决了什么。
4. 如果这一季用本工具完成过实际工作，在本文末尾的「使用记录」加一行，
   只写日期、目标类型、产出数量，不写任何真实资产信息。

## CI 变红时

1. 打开仓库 Actions 页，点红色的那次运行。
2. 展开失败的 job，看最后一个 `##[error]` 之前的那段输出。
3. 本地复现同一个命令（`check_all.py` 里就包含全部检查）。
4. 修完再推。**不要在 CI 红着的时候发版或宣布完成。**

首次公开推送后 CI 会跑 5 个 job（Ubuntu / Windows × Python 3.11 / 3.13 + 浏览器）。
如果只有某一个平台红，优先怀疑路径分隔符、文件锁和 shell 差异。

## 收到 issue 时

| 类型 | 动作 |
|---|---|
| 有可复现步骤的 bug | 复现 → 修 → 加回归测试 → 回复并关闭 |
| 无法复现的 bug | 回一句请求最小复现，14 天无回应则加 `needs-repro` 并关闭 |
| 功能请求 | 先问清使用场景；能落地的进 backlog 并回一句排期口径，不合适的说明原因后加 `wontfix` 关闭 |
| 安全问题 | **不要公开回复**，转到 `SECURITY.md` 的私密渠道 |
| 空白 / 广告 / 无意义 | 直接关闭，不回复 |

关闭不是失礼。个人项目的边界由维护者单方面定义。

## 收到 pull request 时

1. 先看 CI 是否绿。红的一律不合并，不论改动多小。
2. 看范围：只改文档 / 错别字 / 端口 → 合并；改业务逻辑 → 要求先开 issue。
3. 合并用 squash，保持 `main` 线性、一个 PR 一个提交。
4. 合并后本地跑一次 `check_all.py` 再推。

**不接受的情况**：新增运行时依赖、扩大网络能力、把只读改成可写、
在文档里增加未经验证的检测率声明。

## 收到安全报告时

1. 48 小时内回一句「收到，正在确认」。不回比回错更伤。
2. 先复现，再做判断。
3. 成立 → 修 + 回归测试 + 发补丁版本（0.x.y+1）+ 在 Release 说明里写清楚。
4. 不成立 → 直接说明原因。如果属于「设计如此」（例如只监听回环），
   把这一点写进 README 的 `What it is not`，让下一个人不用再报一遍。
5. 不发安全公告，不申请 CVE。这是本地单用户工具，不是基础设施。

## 什么时候宣布休眠

出现任意一条，就在 README 顶部加：

```markdown
> Maintenance status: dormant as of YYYY-MM. Published as-is.
```

- 连续三个月没有打开过本仓库
- 升级依赖需要重写某个模块
- 维护者不再信任它的结论

主动宣布休眠比悄悄烂掉体面。访问者看到「dormant but complete」不会介意，
看到「最后提交一年半前、CI 常红」会介意。

## 不做的事

- 不追 star，不做推广，不写 roadmap
- 不设周更计划
- 不为「看起来在动」而提交不绿的代码
- 不把本项目包装成扫描器或平台 —— 它的价值在于诚实
