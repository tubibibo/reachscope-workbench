# csrf-token：状态变更型 GET 的 CSRF 面

## 1. 你将看到什么

场景里有两条路由：`/`（说明页，内含指向 `/transfer` 的链接）与 `/transfer`（代表一次状态变更）。两个剖面的差异：

| 路由 | baseline | hardened |
|---|---|---|
| `/` | 200，说明页 | 200，说明页（同一页面） |
| `/transfer` | 200，返回"转账已接受"页 | 403，返回"请求被拒绝"页 |

baseline 下 `/transfer` **没有任何校验**：令牌、来源、意图，全都没有，GET 一发就直接"成功"。hardened 下同一条路径返回 403，演示"这类请求应当被拒绝"的行为。

## 2. 操作步骤

1. 打开 ReachScope 实验室页面，选择场景包 `csrf-token`，剖面保持 `baseline`，启动。
2. 用浏览器打开 `http://127.0.0.1:<随机端口>/`，点击页面上的"发起转账（教学演示）"链接。
3. 记录结果：状态码 200、"转账已接受"页面。
4. 再直接在地址栏输入 `http://127.0.0.1:<随机端口>/transfer` 访问一次——**不经过页面、不经过任何确认**，结果同样是 200。这就是"GET 承载状态变更"的问题：它太容易被触发。
5. 回到实验室页面，把剖面切换为 `hardened`（切换以新一代次重启；地址以界面显示为准）。
6. 重复第 2、4 步：同一 URL 现在返回 403 与"请求被拒绝"页面。
7. 在证据面板对比两次采集的状态码（200 → 403）与响应体。

## 3. 为什么

CSRF（跨站请求伪造）的成立条件是：**浏览器会自动带上受害者的身份凭据（Cookie），而服务端分不清"用户本人点的"和"第三方页面触发的"**。

- GET 请求会被 `<a>` 链接、`<img>`、预加载、地址栏直接触发——攻击者只需要让已登录用户打开一个页面，就能静默发出同样的 GET。所以**状态变更不该用 GET**。
- baseline 的 200 展示的是缺陷本身：副作用 + 无校验 + GET，三者叠加。
- hardened 的 403 展示的是期望行为：这类请求应被拒绝。真实系统里的拒绝来自 CSRF 令牌校验、Cookie 的 SameSite 属性、来源检查、把状态变更改为 POST/DELETE 等非幂等方法并要求用户确认。

## 4. 常见误区

- **403 不是"修好了"。** 本场景的 403 是写好的固定响应，场景包里没有、也不该有真实的令牌机制；把"返回 403"当"实现了 CSRF 防护"正是本场景要打破的错觉。
- **CSRF 防护不是"校验 Referer"这么简单。** Referer 可能缺失（见 referrer-policy 场景），单独依赖它既误杀也漏防；令牌 + SameSite + 方法语义才是组合拳。
- **"GET 只读"是约定不是保证。** 缓存、预取、链接分享都会触发 GET；只要 GET 有副作用，这些机制都在替攻击者发请求。
- **换了 POST 不等于完事。** 只改方法而不加令牌/确认，跨站表单照样能伪造 POST。
